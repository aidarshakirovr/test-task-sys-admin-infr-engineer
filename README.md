## Задача 1. Backup и Disaster Recovery (/srv/app/data, ~100 ГБ)

### 1. Выбор инструмента: Restic vs Borg
Для бэкапа 100 ГБ данных выбран **Restic** с выгрузкой в S3-совместимое объектное хранилище (Wasabi / MinIO / AWS S3).

| Критерий | Restic | BorgBackup | Обоснование выбора |
| :--- | :--- | :--- | :--- |
| **Дедупликация** | Блочная на базе алгоритма Rabin Fingerprints (CDC) | Блочная на базе алгоритма Buzzhash (CDC) | Оба решения оптимально сжимают 100 ГБ инкрементов |
| **Нативная поддержка Cloud** | Нативная поддержка S3, SFTP, REST без посредников | Требует отдельного SSH-хоста с установленным Borg | **Restic**: прямая отправка в дешевое S3 без лишних узлов |
| **Защита от перезаписи (WORM)**| Нативная поддержка S3 Object Lock (Compliance mode)| `--append-only` на отдельном сервере | **Restic**: аппаратно-программная защита от удаления |
| **Шифрование** | AES-256-CTR + Poly1305 (Zero-knowledge) | AES-GCM / ChaCha20-Poly1305 | Криптостойкое сквозное шифрование по умолчанию |

### 2. Организация процессов и метрики (RPO / RTO)
* **RPO (Recovery Point Objective):** <= 4 часа. Запуск снапшота каждые 4 часа. Блочный инструмент Restic обрабатывает только изменившиеся блоки (для 100 ГБ это обычно 1–3 ГБ за окно), что занимает 2–3 минуты и не нагружает диск.
* **RTO (Recovery Time Objective):** <= 30 минут. Загрузка 100 ГБ по 1 Gbps каналу занимает ~15 минут; развертывание и проверка целостности сервиса — ~10 минут.
* **Retention Policy (политика хранения):**
  * Последние 24 часовых снапшота (`--keep-hourly 24`)
  * Ежедневные за 14 дней (`--keep-daily 14`)
  * Еженедельные за 4 недели (`--keep-weekly 4`)
  * Ежемесячные за 6 месяцев (`--keep-monthly 6`)
  * Очистка выполняется через `restic forget --prune`.
* **Безопасность секретов:** Пароли и ключи S3 не хранятся в открытом коде, монтируются в `/etc/restic/` с правами `0400` только для сервисного пользователя или доставляются через HashiCorp Vault.

### 3. Защита от Ransomware, компрометации и удаления
1. **S3 Object Lock (WORM):** Бакет переводится в режим `Compliance`. Даже если злоумышленник получит права root на сервере с ключами, API S3 отклонит попытки модификации или удаления существующих снапшотов.
2. **Least Privilege на сервере:** Скрипты бэкапа исполняются от системного пользователя `restic-backup` (без shell-доступа), а доступ к `/srv/app/data` ограничен правами Read-Only через POSIX ACL.
3. **Изоляция Prune/Forget:** Задачи удаления старых бэкапов запускаются не с продуктового сервера, а с изолированного контура управления.

### 4. Автоматизация (Ansible)
Инфраструктура развернута ролью `ansible/roles/backup_restic`:
* Создает сервисного пользователя и защищенные каталоги.
* Разворачивает скрипт `backup-app.sh`.
* Создает и включает `systemd.timer` (расписание каждые 4 часа с рандомизацией нагрузки `RandomizedDelaySec=300`).
* Протестирована на **строгую идемпотентность** (`changed=0` при повторном запуске).

### 5. Регламент Disaster Recovery (DR-тестирование)
* **Еженедельная проверка целостности:** Автоматический запуск `restic check --read-data-subset=5%` для поиска поврежденных блоков (bit rot).
* **Ежемесячный автоматический DR-Smoke Test:** Скрипт `scripts/dr-restore-test.sh` в изолированном контейнере разворачивает последний снапшот, проверяет контрольные суммы и валидирует тестовый запуск сервиса.

## Задача 2. Production Incident: Сетевая недоступность Docker-сервиса

### Симптомы
Контейнер работает, локально отвечает (`localhost`), но внешние клиенты сети не могут подключиться.

### Пошаговый план диагностики

1. **Проверка привязки портов (Socket Binding):**
   * *Команда:* `ss -tulpn | grep :8080` или `docker port <container_name>`.
   * *Причина:* Порт опубликован как `127.0.0.1:8080:80` вместо `0.0.0.0:8080:80`. Пакеты из внешней сети сбрасываются ядром на уровне сокета.
2. **Проверка IP Forwarding ядра Linux:**
   * *Команда:* `sysctl net.ipv4.ip_forward`.
   * *Причина:* Если значение равно `0`, ядро не пересылает транзитный трафик в мост `docker0`.
   * *Фикс:* `sudo sysctl -w net.ipv4.ip_forward=1` и фиксация в `/etc/sysctl.d/99-docker.conf`.
3. **Проверка цепочек Docker в iptables и UFW:**
   * *Команды:* `sudo iptables -nvL FORWARD` и `sudo iptables -t nat -nvL DOCKER`.
   * *Причина:* Сброс кастомных цепочек Docker фаерволом или блокировка в цепочке FORWARD в UFW (`DEFAULT_FORWARD_POLICY="DROP"`).
4. **Конфликт сетевых подсетей (Subnet Collision):**
   * *Команды:* `ip route` и `docker network inspect bridge`.
   * *Причина:* Пересечение внутренней подсети Docker (`172.17.0.0/16`) с корпоративной LAN-сетью.
   * *Фикс:* Настройка пула `default-address-pools` в `/etc/docker/daemon.json`.
5. **Сквозной анализ трафика (tcpdump):**
   * *Команда:* `sudo tcpdump -nn -i any port 8080 -v`.
   * Позволяет убедиться, доходят ли входящие TCP SYN пакеты до хоста и моста контейнера.

### Безопасное внедрение сетевых изменений в Production
1. **Безопасное применение Netplan:** Использование команды `sudo netplan try --timeout 120` (автоматический откат при потере SSH-доступа).
2. **IaC и Staging:** Конфигурации сети раскатываются через Ansible с обязательным прогоном `--check --diff` на тестовом стенде.
3. **Out-of-Band (OOB) доступ:** Наличие независимого канала управления (IPMI / iDRAC / консоль гипервизора).
4. **Blackbox-мониторинг:** Внешний контроль доступности сервисов синтетическими проверками (Prometheus Blackbox Exporter).
